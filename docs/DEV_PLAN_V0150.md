## 3) الموجات وبوابات القبول (كل موجة تُقاس قبل التالية)

### الموجة 0 — عقد الاستيراد الموحد (منفذة، ملتزمة)
- `mizan.finding.v1` مع حفظ المصدر حرفيًا + `import-sarif` مستقل عن الأداة + فشل صريح بخرج 2 على كل صيغ الرفض.
- بوابة القبول: 42 اختبارًا للموجتين، العدّاد المقاس في README، بوابة الوثائق خضراء، السلبيات الذهبية 0.

### الموجة 1 — الربط لا المحو + الترياج + البوابة الخارجية (منفذة، ملتزمة)
- `merge-findings`: مجموعات بالبصمة الثابتة تحفظ كل ورود بحرفه — حذف تقرير لا يمحو أدلة غيره (مثبت باختبار انحدار).
- `triage`: قرارات مراجعة موثقة فقط — بصمة غير موجودة = فشل صريح (رفض `# nosec` الأعمى)؛ كل قرار يختم `triage_source: review-file`.
- `mizan.external_gate.v1`: حجب بمطابقة تامة للشدة الحرفية؛ `unknown` لا يحجب؛ المُراجَع لا يحجب.
- بوابة القبول: نفس معايير الموجة 0 + اختبار انحدار «حذف تقرير ≠ محو أدلة».

### الموجة 2 — القياس المستقل المنشور (التالية)
- مجموعة قياس ثابتة في `tests/benchmark`: إيجابيات معروفة لكل قاعدة، سلبيات مشابهة شكليًا، حالات حدية (تعليقات/اختبارات/مولّد/متعدد الأسطر).
- موصل تشغيل اختياري واحد (Semgrep) بإصدار مثبت وقت التبني، ينتج SARIF يمر عبر الموجة 0.
- تقرير precision/recall بالمنهجية والعينة والأوامر والقيود — منشور في `docs/MEASUREMENT.md`، مفصولًا المعلوماتي عن الأمني.
- بوابة القبول: تشغيل متكرر يعطي النتائج نفسها؛ أي فشل أداة يظهر incomplete لا نظيف.

### الموجة 3 — طلب الإصلاح المنظّم لوكيل البرمجة
- `mizan.finding.v1` → `repair-request.v1`: finding_id، الدليل، الإصلاح المقترح، القيود، اختبارات التحقق، `confidence`، `human_review_required=true`.
- MIZAN لا يكتب في شجرة المستخدم في هذه الموجة؛ الوكيل يعمل في فرع/نسخة منفصلة ويعرض diff ونتائج الاختبارات، والدمج بموافقة بشرية.
- بوابة القبول: مخطط JSON مُتحقق منه + اختبار أن الطلب يرفض الدليل غير الكافي («لا تخمّن؛ اشرح ما يلزم للتحقق»).

### الموجة 4 — التحقق المعزول من الإصلاح (لاحقًا)
- نسخة مؤقتة معزولة (git worktree) ← تطبيق التغيير ← اختبارات بلا أسرار وبلا شبكة افتراضيًا ← diff + نتيجة ← موافقة صريحة ← نقل أو حذف.
- تقرير التحقق يذكر: الملفات المتغيرة، الاختبارات الشُغّلة وغير الشُغّلة، بقاء بصمات الأصل، حدود العزل.
